# SDK ownership and behavior baseline

Baseline: commit `e5364af`, inspected 2026-09-27 before SDK extraction. This document records the source behavior, not a claim that the migration acceptance checks have passed. The target architecture is backend-agnostic.

**Verification update — 2026-09-29:** Generated API/ABI snapshot gates have been removed. This behavioral and storage baseline remains historical context; current acceptance uses public contract review, behavioral tests, module boundaries and publication validation.

Historical source paths below are intentional: they identify the code and storage owners at that baseline. The later 2026-09-28 structural migration moved provider implementations into `sdk/providers/<provider>`. The subsequent optional-presentation extraction moved provider artwork/mappers into `sdk/providers/<provider>/ui` and shared presentation contracts/error strings into `sdk/ui`; application rendering and DI stayed outside SDK artifacts. The initial structural extraction preserved Kotlin names; `0.1.0-alpha02` subsequently replaces the public namespaces and consumer interfaces without aliases. Maven artifact names and persisted data identifiers remain stable. Use [the current integration reference](integration.md) and [alpha02 migration guide](alpha02-migration.md) for implementation, while retaining this baseline for legacy behavior and persistence attribution.

**Storage supersession — 2026-10-02:** There are no shipped-data compatibility requirements. The current SDK has removed legacy conversion, owner mappings, backup/quarantine and alternate application filenames. Providers and applications use the existing namespaced defaults; old development files/keys remain untouched and are not imported. The legacy storage inventory below is historical, not an implementation requirement. Current account/profile isolation and the auth/context storage availability check remain.

## Existing behavioral baseline

### Authentication and lifecycle

* TMDB construction has no network call. `bootstrapAuth` reads persisted session, validates it using movie account states, then verifies account details only when a configured account ID is present. Without configuration it currently returns `LoggedIn(account = null)`. This is an intentional migration correction: discover the authenticated account first, then apply optional expected-account restriction.
* Current shared `AuthAccountModel.id` is `Int`. TMDB profiles are partitioned by configured account ID, not the identity returned by authentication. ClientB stores only a logged-in boolean and produces a null account. It is a simulated provider, not evidence of real backend authentication.
* TMDB login validates credentials before revoking a retained session. A failed retained-session revocation prevents replacement. A newly created but uncommitted remote session is compensated best-effort. A local save that throws after committing is reconciled; a committed session must not be deleted during cancellation.
* Remote logout failure retains the local session/authenticated state for retry. Successful remote revocation followed by failed local cleanup records the revoked ID in memory; retry must not repeat deletion. Cancellation propagates. Authoritative unauthorized/expired logout transitions out of authenticated state even if cleanup fails, while preserving the primary failure.
* Transient bootstrap/network/timeout/parse failures retain persisted credentials for retry. Authoritative rejection clears them. The existing application can orchestrate invalidation; runtime must become the single owner without converting all authentication failures into session invalidation.
* Current repositories have no unified instance close/ownership or session-generation mechanism. Migration must add idempotent resource close without logout, prevent duplicate storage owners and reject late results from obsolete account/session context.

### Validation, search and local state

* Login validation requires trimmed nonblank identifier and nonblank password. Password whitespace is not normalized. The login use case only forwards values, so direct repository calls bypass shared validation today.
* Profile validation trims display name, requires 1â€“32 characters, requires avatar/parental selections and checks membership when options are supplied. Current create/update use cases trim names; provider profile implementations validate selection IDs but are not the authoritative shared validator.
* Search normalization trims and collapses `\\s+` to one space; minimum searchable normalized length is 3. Search result limit is 20 and discovery limit is 6 in both current providers. History retains the latest 5 queries per profile, deduplicated/removed case-insensitively, preserving the most recent spelling.
* `SearchViewModel` currently owns the common event sequence: typing does not record history; submit/recent selection records a successfully displayed query; selecting a result records its result query once. Equivalent queries/repeated submit avoid duplicate requests, submit upgrades a pending debounce, stale results are ignored, retry executes again. UI debounce (300 ms), delayed skeleton (150 ms), focus and navigation stay in the app. Do not introduce a new SDK retry/cache policy while moving the existing history coordinator.
* Library membership has independent nullable `likedAtMillis` and `addedToMyListAtMillis`. Re-adding existing membership preserves its original timestamp; removing one preserves the other; removing the final membership removes the entry. Aggregate storage observation sorts by newest membership timestamp, then content ID. Liked/my-list output sorts by that membership's timestamp. Continue watching comes from progress, with logical row IDs `library:continue-watching`, `library:liked`, `library:my-list`.
* Progress is resumable at **30,000 ms inclusive**, with known positive duration and fraction **strictly below 0.95**. Invalid/completed upsert removes existing progress; retain newest 50 entries per profile. Stored snapshots clear nested `playbackProgress`. Observation is newest update first.
* `PlayerViewModel` saves while playing when crossing a 10,000 ms bucket and on pause/seek/scrub completion/back/background events. Unknown duration must preserve previous resume data. Persistence errors must not interrupt playback or player exit; cancellation is rethrown. Runtime event coordinator should accept explicit events while engine rendering/session ownership and interaction state remain application-owned.

### Content policy and capabilities

* TMDB reference profiles are local: immutable owner `tmdb-profile-owner`, deletable kids profile `tmdb-profile-kids`, and monotonically numbered `tmdb-profile-created-<n>` profiles. Snapshot schema validates unique IDs and the next ID counter. Profile options are all/teen/kids, but existing filtering is only `includeAdult = !profile.isKidsProfile`.
* Home/search/trending/recommendations resolve the profile from the current local snapshot and filter backend `adult` flags for kids. **Direct TMDB details currently bypass profile existence/content policy**. Both source resolvers bypass context/policy. Saved library/progress snapshots have no policy enforcement. These are explicit corrections; do not interpret `pgRatingLevel` as a universal maturity policy.
* TMDB QR login and password recovery return success without work. ClientB password recovery does likewise; its credential/QR login is simulated. SDK capabilities must distinguish support and reference behavior, returning explicit unsupported results where no operation exists.
* TMDB source resolver returns Shaka's Sintel DASH sample for every catalogue item. ClientB returns the pinned Roku trick-play DASH sample for every item. Current `assetId` and title reuse requested catalogue metadata, so consumers cannot distinguish demo media. Migration must expose demo playback explicitly in config/capabilities/source metadata and preserve the app demonstration flow.

## Persistence contract and migration hazards

Android calls `preferencesDataStoreFile(name)` for the names below. Preserve that call's actual path behavior; in particular several legacy constants already include `.preferences_pb`. Browser stores use DataStore `PreferencesSerializer` with `WebLocalStorage` or `WebSessionStorage` and the same supplied names. Do not invent a browser JSON envelope: only the individual string preference values below are JSON.

| Store name passed to platform | Keys / representation | Ownership and behavior |
| --- | --- | --- |
| `tmdb_auth.preferences_pb` | `session_id`: string; `account_id`: int; `account_username`, `account_display_name`: strings | `TmdbPreferencesAuthStore.saveSession` writes session/account together. Cleanup removes only these keys, preserving profile snapshots and unrelated preferences. Preserve integer legacy account decoding when introducing string IDs. |
| Same TMDB auth store | `profiles_json.account_configured_<hex>` or `profiles_json.account_unconfigured`: JSON `{schemaVersion,nextProfileNumber,profiles}` with provider `ProfileDto` fields | Configured account suffix encodes **each UTF-16 code unit as four lowercase hex digits**. Blank/whitespace configuration shares the unconfigured key. Schema version is 1; read/mutation uses transactional DataStore edit. Missing key creates defaults; malformed data yields parsing failure without overwriting it. |
| Same TMDB auth store, browser coordinator | `web_selected_profile_id.<hex>`: string profile ID | Account suffix uses **UTF-8 bytes as two lowercase hex digits**, different from the profile snapshot encoding. Requires nonblank configured account. Restore verifies selected ID against current profiles and clears deleted selection. Logout/invalidation clears selection, retaining profile data. |
| `client_b_auth` | `is_logged_in`: boolean | No persisted account identity. No trustworthy inferred owner exists for legacy ClientB account-owned data unless an explicit mapping is supplied. |
| `search_history.preferences_pb` | `recent_searches_json`: JSON `{queriesByProfile: {profileId: [query]}}` | Profile-only, no account/provider partition, no schema version. Read errors and malformed JSON currently become empty values; a later mutation can overwrite malformed input. |
| `library.preferences_pb` | `library_json`: JSON `{version:1, entriesByProfile:{profileId:[entry]}}` | Profile-only partition. Entry has `content`, `likedAtMillis`, `addedToMyListAtMillis`. Content snapshot fields: `id,title,rating,pgRatingName,pgRatingLevel,poster,backdrop,releaseDate,genres`; description/cast/progress/trailers are not persisted. Parse failures return `AppError.Parsing`; data is not replaced. Version defaults to 1 but existing decoder does not reject future versions. |
| `playback_progress.preferences_pb` | `entries_json`: JSON list of `PlaybackProgressEntryModel` (`profileId,contentId,contentSnapshot,positionMillis,durationMillis,updatedAtMillis`) | Profile-only partition, no version. Full serializable content snapshot. Read errors and malformed JSON currently become empty list, later writes can overwrite malformed input. |

JSON bindings generally use `ignoreUnknownKeys = true`. Android/browser corruption handlers can replace an unreadable preference store with empty preferences; this is distinct from malformed JSON inside a valid preferences store and must be considered by migration fixtures.

Migration requirements:

1. Scope every new account-owned store by provider/backend environment, explicit storage namespace, authenticated opaque account ID and subprofile ID. Encode components injectively, preserving non-ASCII identifiers. Never concatenate ambiguous raw delimiters.
2. Copy/transform legacy snapshots only after identity is established through trusted persisted authentication or an explicit mapping. Configured expected-account restriction alone is not proof of the signed-in account. Logged-out/unconfigured/unowned data must remain quarantined and preserved; never give it to the next login.
3. Record a versioned completion marker in the same transaction as newly partitioned values where possible. Restart after interruption must neither duplicate nor discard data. Keep original data until attribution and durable completion are established. Malformed data should be retained for recovery, not replaced by an empty migration result.
4. Preserve profile IDs, profile next-number counters, history order/case, membership timestamps and progress snapshots/retention. Account A â†’ logout â†’ B â†’ A must recover A's data even where A and B have identical subprofile IDs.
5. Successful logout removes credentials and active profile context only. `close()` releases owned resources only. Account history/library/progress survive both operations.

## Dependency and acceptance gates

Current `playback:api` uses the Compose KMP convention and exposes `compose.ui`; it must be split before headless source/progress Wasm tests can prove no Compose/Skiko closure. Current provider data includes Koin, DataStore and Ktor; numerous feature domain/data modules also carry Koin wiring. The SDK may privately use storage/transport implementations but consumer API and published closure must exclude Koin, UI and rendering engines. Public API signature dependencies must use `api` scope where necessary; current `core:domain` hides models/coroutines with `implementation`.

Acceptance must demonstrate all of the following, without relying on a StreamCore ViewModel to enforce a rule:

* Public client bootstrap/login with no expected-account restriction discovers stable non-null identity, loads provider profiles, browses/searches, mutates retained local state, logs out and closes.
* A staged `0.1` candidate Maven repository contains the complete SDK dependency closure. Separate Android and headless Kotlin/Wasm consumers use coordinates only, no project dependency/composite substitution/checkout source or hidden direct dependencies.
* Runtime contracts test validation/capabilities/context/policy/history/library/progress, transient and authoritative errors, cancellation, storage failure, concurrent independent instances, late A-session results after B login and A â†’ B â†’ A retained data.
* Consumer API, provider factory/configuration/extensions and runtime provider-integration public contracts are reviewed for intentional changes and consumer impact; boundary checks prohibit feature integration-port imports and public raw provider/storage implementations.
* Existing Android flavors compile, TMDB Wasm builds/runs, and representative mobile/tablet/TV/browser navigation and rendering are reviewed using `docs/agent-workflow.md`. Baseline inventory is not a substitute for these checks.
* Provider onboarding documents adapter/configuration/capabilities/factory/testing/application wiring. ClientB evidence is structural substitutability only. JS/TS and Swift distribution remain subsequent milestones.
